# 阶段 4：最终检查、记录与收尾

> 目标：在用户认可代码与课程文本后，对当前讲次做最终检查，更新事实账本和进度表，形成可继续下一讲的稳定状态。

## 前置条件

- 阶段 2 的代码改动已被用户认可，或本讲无需代码改动。
- 阶段 3 的课程文本已被用户认可。

## 工作步骤

1. **最终文件检查**
   - `git diff --check`。
   - Markdown 相对链接检查。
   - 源码入口、阅读清单、练习路径存在性检查。
   - Mermaid 解析 / 渲染检查；如无工具，记录人工检查。

2. **构建与测试记录**
   - 若本讲有代码改动，确认构建和相关测试已运行。
   - 若用户已手动测试，记录用户反馈。
   - 若某项验证无法运行，记录原因和风险。

3. **事实账本更新**
   - 共享事实、版本、数字口径。
   - 代码片段锚点。
   - 跨讲承诺和兑现状态。
   - 全局一致性待查项。

4. **进度表更新**
   - 将当前讲次标记为完成。
   - 记录每阶段完成情况、验证范围、用户确认状态和 backlog。
   - 若有后续讲次需要同步，写入 backlog 或事实账本。

5. **收尾汇报**
   - 给出简短总结。
   - 明确当前讲是否完成。
   - 不自动进入下一讲，等待用户指示。

## 输出格式

阶段 4 的回复应包含：

- **最终状态**：当前讲是否完成。
- **最终验证**：命令、检查项和结果。
- **记录更新**：事实账本和进度表更新了什么。
- **剩余风险**：若无则说明无已知剩余风险。
- **下一步**：等待用户指示进入下一讲。

## 禁止事项

- 不在收尾阶段引入新功能或大段新内容。
- 不把未跑的测试写成已跑。
- 不跳过事实账本和进度表。

## 全局一致性

L00-L26 全部完成后，额外做一轮全局一致性检查：

- 共享数字、版本、schema、系统数量、目录结构是否一致。
- 同一个类、函数、数据字段、Lua API、DebugPanel 或工具名是否一致。
- “详深留 Lxx”“下一讲展开”“铺垫 Lxx”等跨讲承诺是否兑现。
- 代码改动引起的路径、片段、图示和练习是否已全部更新。
- 大纲与 27 篇正文是否仍保持同一课程路线。
