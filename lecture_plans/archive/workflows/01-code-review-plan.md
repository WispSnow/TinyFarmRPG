# 阶段 1：代码审阅 + 修订计划

> 目标：针对当前讲次覆盖的代码做审阅，给出修订计划，等待用户确认。此阶段默认不修改源码、不修改讲义正文。

## 输入

- 当前讲义：`lecture_plans/lectures/NN-*.md`
- 大纲对应小节：`lecture_plans/tinyfarmrpg-course-outline.md`
- 事实账本：`lecture_plans/workflows/fact-ledger.md`
- 进度表：`lecture_plans/workflows/progress.md`
- 代码规范：`for_agent/code-guide.md`
- 若涉及 RmlUi：`for_agent/rmlui-guide.md`
- 若涉及弹出场景 UI：`for_agent/ui-style-guide.md`

## 工作步骤

1. **确定覆盖范围**
   - 从讲义和大纲提取本讲涉及的源码、数据、脚本、UI、测试和工具。
   - 对照事实账本，找出已有共享事实和跨讲承诺。

2. **源码取证**
   - 用 `rg` 查找讲义提到的类名、函数名、事件名、组件名、数据字段和工具名。
   - 打开关键源码入口，确认当前实现与讲义覆盖范围是否一致。
   - 若讲义贴了真实代码片段，记录 `文件 + 符号` 锚点。

3. **代码审阅**
   - 按 `for_agent/code-guide.md` 检查现代 C++、RAII、无异常、不过度防御、Doxygen 注释。
   - 检查模块边界：`engine` / `game` 依赖方向、domain service、command / event、Lua 内容层、数据目录。
   - 检查关键失败路径是否有测试覆盖。
   - 若涉及 UI，检查 RmlUi 资源、样式、scene / overlay 责任边界。

4. **影响面扫描**
   - 若可能需要 rename / move / 接口签名 / 数据字段变更，先用 `rg` 扫描 `lecture_plans/lectures` 和相关源码引用面。
   - 记录可能影响的讲次，作为计划的一部分交给用户审阅。

5. **形成计划**
   - 将问题按优先级分为：必须先改、建议改、课程说明、后续 backlog。
   - 给出最小代码修订方案、测试方案、风险和需要用户确认的问题。

## 输出格式

阶段 1 的回复应包含：

- **审阅范围**：本讲覆盖了哪些代码和资源。
- **主要发现**：按严重程度列出问题，带文件路径和证据。
- **修订计划**：准备怎么改，改哪些文件，为什么。
- **测试计划**：阶段 2 完成后应运行哪些构建 / 测试 / UI 检查。
- **跨讲影响**：可能影响哪些后续讲义或事实账本条目。
- **等待确认**：明确说明尚未执行代码修订，等待用户审阅计划。

## 禁止事项

- 不直接修改源码。
- 不直接扩写课程正文。
- 不把未验证的推断写成事实。
- 不为了风格 nit 发起大范围重构；教学准确性和核心质量优先。

## 进度记录

阶段 1 完成后，可将 `lecture_plans/workflows/progress.md` 中当前讲次状态标记为“阶段 1 待审阅”。若用户希望计划先不落盘，则只在回复中给出计划。
