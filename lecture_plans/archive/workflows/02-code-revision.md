# 阶段 2：执行代码修订

> 目标：在用户认可阶段 1 计划后，执行代码修订并完成必要验证。完成后等待用户审阅和测试。

## 前置条件

- 用户已经认可阶段 1 的修订计划，或明确指定要执行的代码改动。
- 当前工作树可能已有用户改动，必须先查看并避免覆盖。

## 工作步骤

1. **复核计划与工作树**
   - 读取阶段 1 计划、事实账本和进度表。
   - 用 `git status --short` 查看工作树。
   - 对将要修改的文件先读当前内容，确认没有未理解的用户改动。

2. **执行代码修订**
   - 使用 `apply_patch` 做手工编辑。
   - 保持改动范围贴合已确认计划。
   - 遵守 `for_agent/code-guide.md`。
   - 如涉及 RmlUi 或弹出 UI，遵守对应 UI 指南。

3. **同步受影响引用**
   - 若改了类名、函数名、文件名、事件名、数据字段或路径，用 `rg` 扫描源码和 `lecture_plans/lectures`。
   - 当前讲义可暂不扩写，但必须记录会影响哪些课程文本。
   - 更新事实账本的代码改动影响面和共享事实。

4. **验证**
   - 使用 ninja 构建项目。
   - 运行本讲相关测试；若测试目标不明确，先用 `ctest -N` 或 `rg` 查找相关测试。
   - 如果涉及 UI，验证资源路径、RML/RCSS、场景注册和必要 smoke test。
   - 如果无法运行某项验证，记录原因。

5. **交付等待**
   - 汇总代码改动、验证结果和剩余风险。
   - 停下来等待用户审阅代码和运行测试。

## 输出格式

阶段 2 的回复应包含：

- **代码改动**：改了哪些文件和核心行为。
- **计划偏差**：是否偏离阶段 1 计划，为什么。
- **验证结果**：运行了哪些命令，结果如何。
- **影响记录**：更新了哪些事实账本条目，哪些讲义后续要同步。
- **等待确认**：明确说明下一步是用户审阅 / 测试，通过后再进入阶段 3。

## 禁止事项

- 未经确认不扩大重构范围。
- 不顺手扩写课程正文。
- 不回滚用户未要求回滚的改动。
- 不在测试失败时掩盖失败原因。

## 进度记录

阶段 2 完成后，将 `lecture_plans/workflows/progress.md` 中当前讲次状态标记为“阶段 2 待用户测试 / 审阅”，并记录构建、测试和剩余风险。
