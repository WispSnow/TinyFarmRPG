# 第1课 游戏架构设计：从"new 一切"到声明式装配

上节课我们铺开了整门课的地图。这节课正式进入项目内部——站在 `GameScene::init()` 面前，看 TinyFarmRPG 如何在一个接近 5 万行的底座上，继续"长"出一个能支撑 JRPG 的工程结构。

先回忆一个画面：上一期 TinyFarm 的 `GameScene::init()` 里，三十多个 `make_unique<XxxSystem>(...)` 排成一条长龙，谁先谁后全靠注释和经验。功能再多一倍，这个函数就要炸了。

这一期彻底翻新了这件事：catalog、service、system 的创建被拆到一组工厂里，`GameScene` 自己只剩下两行——"装 service"和"装 system"——其余什么都不管。

```mermaid
flowchart TD
    GS["GameScene::init()"] --> GRA["GameRuntimeAssembler<br/>装配 facade"]
    GRA --> RSF["RuntimeServiceFactory<br/>catalog + 长期服务"]
    GRA --> SF["SystemFactory<br/>ECS systems"]

    RSF --> RCL["RpgCatalogLoader<br/>actors / classes / skills / states / equipment / enemies / troops"]
```

> 这张图的核心信息就一个：`GameScene` 不再"创建"任何 service 或 system。它只是把自己交给 `GameRuntimeAssembler`，由后者按顺序委托给两个 Factory。记住这个"委托"的感觉，后面所有细节都是它的展开。

## 核心知识点

### 1. 回顾：上一期的两层架构

上一期 [part-02](../ref/OpenGL与迷你农场/02-游戏架构设计.md) 建立了清晰的两层：

- **engine 层**：渲染、输入、音频、资源、ECS 框架、Scene 栈、UI 框架——这些"和具体游戏无关"的能力。
- **game 层**：TinyFarm 特定的玩法、组件、系统、数据目录、UI 控件。

依赖方向是单向的：`game → engine`，引擎层绝不 `#include` 游戏层。

这两层在 TinyFarmRPG 里完整保留。但问题来了：**仅靠两层已经不够用了**。任务、商店、装备、战斗、Lua 内容层一拥而上——"原子写入规则"和"剧本式内容编排"如果继续直接写在 system 里，system 会越来越胖、越来越难测。

所以就有了下面的扩展。

### 2. 新增的两个分层：domain 与 script

TinyFarmRPG 在两层之上又拆出两个新角色：

```mermaid
flowchart TB
    Eng["engine<br/>渲染 输入 资源 ECS Scene UI"] --> Game["game<br/>组件 系统 数据"]
    Game --> Domain["domain<br/>规则真相<br/>Inventory / Equipment / Quest / Shop ..."]
    Game --> Script["script<br/>内容编排<br/>NPC 对白 / 任务分支 / 剧情触发"]
    Script -.->|"发请求"| Domain
```

- **domain 层**（`src/game/domain/`）：把"会改变玩家状态的写入操作"集中到一组**领域服务**里。`InventoryDomainService`、`EquipmentDomainService`、`QuestTurnInService`、`ShopTransactionService` 都属于这一层。它的职责是**规则真相**——preflight 校验、原子写入、反馈事件。详细内容会在 [领域服务与命令事件边界](02-领域服务与命令事件边界.md) 和 [任务系统](10-任务系统.md) 中展开。
- **script 层**（`scripts/` + `src/game/script/`）：Lua 内容脚本和 C++ 绑定。它的职责是**内容编排**——NPC 对白、任务分支、剧情触发。详细内容会在 Lua 内容层三节课（[总览](06-Lua内容层总览.md) / [ScriptHost 与 Sol2 绑定](07-ScriptHost与Sol2绑定.md) / [脚本事件桥与 Tiled 接入](08-脚本事件桥与Tiled接入.md)）中展开。

> **为什么要拆出这两层？** 一句话：**写入规则要绝对集中，写入触发要绝对灵活。**
>
> domain 集中，是为了让"加物品 / 卖物品 / 装备武器 / 交付任务"这类状态变更——不管是从 system、UI、Lua 脚本还是存档恢复哪条路径触发——都走同一套规则校验。
>
> script 灵活，是为了让"NPC 在晴天和雨天说不同的话"、"完成某个任务后商店多卖一件东西"这种内容变化不需要重新编译 C++。

### 3. 装配模式：从"new 一切"到"声明式装配"

回到 TinyFarm 的 `GameScene::init()`——三十多个 `make_unique<XxxSystem>(...)` 排成长列，依赖顺序靠注释和工程师的记忆维护。功能再翻一倍，这个文件就炸了。

TinyFarmRPG 把它彻底重构。来看新项目的 `GameScene::init()` 核心：

```cpp
bool GameScene::init() {
    if (!game::runtime::GameRuntimeAssembler::assembleServices({
            *this, context_, registry_, game_time_, *services_})) {
        return false;
    }
    if (!game::runtime::GameRuntimeAssembler::assembleSystems({
            context_, registry_, *services_, *systems_})) {
        return false;
    }
    // ... 输入上下文、UI、事件订阅、首帧同步 ...
}
```

两行装配，干净利落。`GameScene` 不再自己 new 任何东西，它把"装配"这件事完全委托给一组工厂。下面这六个角色各司其职：

| 角色 | 文件 | 职责 |
| --- | --- | --- |
| `GameRuntimeAssembler` | `runtime/game_runtime_assembler.*` | **外观入口**，把"装 service"和"装 system"两件事拆开委托 |
| `RuntimeServiceFactory` | `runtime/runtime_service_factory.*` | 创建并加载所有长期 service（catalog / WorldState / MapManager / SaveService / ScriptHost …） |
| `SystemFactory` | `runtime/system_factory.*` | 先补齐缺失的 domain service，再创建 40+ system / bridge 实例 |
| `GameRuntimeServices` | `runtime/system_bundle.h` | 持有 service / catalog 所有权的 struct |
| `GameSystemBundle` | `runtime/system_bundle.h` | 持有 system 实例所有权的 struct |
| `SystemScheduler` | `runtime/system_scheduler.*` | 不拥有 system，只在固定步里**引用** bundle 来推进 |

```mermaid
flowchart LR
    A["GameScene"] --> B["GameRuntimeAssembler"]
    B --> C["RuntimeServiceFactory"]
    B --> D["SystemFactory"]
    C --> E["GameRuntimeServices<br/>所有权"]
    D --> F["GameSystemBundle<br/>所有权"]
    E --> G["SystemScheduler<br/>只引用"]
    F --> G
```

**这个改造具体解决了什么？**

- **依赖可见**。service 和 system 各自被独立列表化，依赖关系写在工厂参数表里，一眼看穿——不再靠注释和"我记得那个要先初始化"。
- **顺序由数据描述**。哪个 catalog 先加载、哪个 service 在哪个 catalog 之后创建，全部由 `assemble()` 内部的固定流水线决定，而不是散落在各处。
- **测试友好**。要单元测试一个 system，只需构造它依赖的那几项 service，不必把整个 `GameScene` 拉起来。
- **新增路径固定**。新增 catalog / service / system 时，沿着 manifest → services struct → factory → scheduler 这几处登记就行。要动的点多了一些，但每一步都有明确的"该在哪改"。

### 4. Service 装配顺序：先数据，再世界，最后脚本

`RuntimeServiceFactory::assemble` 内部有一条严格的流水线。**顺序就是依赖**——不是"建议"，是硬约束：

```mermaid
sequenceDiagram
    participant RF as RuntimeServiceFactory
    participant CL as ContentCatalogLoader
    participant WS as WorldState
    participant MM as MapManager
    participant SS as SaveService
    participant SH as ScriptHost

    RF->>RF: 注入 ResourceManager 到 registry.ctx
    RF->>CL: 加载 Blueprint / Item / Appearance / VFX / RPG / Quest / Shop
    RF->>RF: 注入 catalog 指针, 初始化 Localization / AudioCue
    RF->>RF: 创建 CollisionResolver, 加载 GameTime / UserSettings
    RF->>WS: 加载 farm-rpg.world
    RF->>RF: 创建 EntityFactory
    RF->>MM: 创建 MapManager, 注册预加载资源
    RF->>RF: 预加载已登记资源
    RF->>SS: 创建 SaveService
    RF->>MM: 加载初始地图 home_exterior
    RF->>RF: 配置相机 / VFX backend
    RF->>SH: 启动 ScriptHost, 执行 scripts/bootstrap.lua
```

逐一拆解"为什么是这个顺序"：

- **Catalog 先于一切。** 后续 system 和 service 都要查这些静态规则：`InventoryDomainService` 依赖 `ItemCatalog`、`QuestTurnInService` 依赖 `ItemCatalog`、`EquipmentDomainService` 依赖 `RpgCatalog`。catalog 加载失败会直接 `return false` 中断装配——没数据，后面全白搭。
- **WorldState 先于 MapManager。** `MapManager` 构造函数会读 `WorldState` 里的世界图（neighbors / triggers）。世界结构都没建立，地图管理器无从工作。
- **MapManager 先于 SaveService。** 存档需要回写"当前在哪张图、地图里实体快照如何还原"——这些信息由 MapManager 提供。
- **ScriptHost 是 service 装配的最后一步。** 脚本里的 `tf.quest.status(...)`、`tf.shop.open(...)`、`tf.map.travel(...)` 等 API，需要 catalog、WorldState、MapManager、Localization 等运行期服务全部就位。Lua 发出的玩法请求会先进入 dispatcher，后续由 `SystemFactory` 补齐的 domain service 和 gameplay system 处理。所以 ScriptHost 必须最后一个启动。

> **动手小练习**：打开 [`runtime_service_factory.cpp`](../../src/game/runtime/runtime_service_factory.cpp)，看 `assemble()` 主函数，数一数它在哪些前置条件失败时 `return false`。这些就是装配失败时的"硬停点"，每一个都对应上面流水线的某个依赖前置。

### 5. ContentCatalogLoader 与 RpgCatalogLoader：集中加载，集中校验

如果说"工厂"管的是"谁先创建谁"，那 `ContentCatalogLoader` 管的就是"内容数据从哪读"。

所有数据路径集中定义在 [`game_content_manifest.h`](../../src/game/runtime/game_content_manifest.h)：

```cpp
struct GameContentManifest final {
    static constexpr const char* ActorBlueprints = "assets/data/actor_blueprint.json";
    static constexpr const char* Items           = "assets/data/item_config.json";
    static constexpr const char* AppearanceCatalog = "assets/data/appearance_catalog.json";
    static constexpr const char* RpgManifest     = "assets/data/rpg/manifest.json";
    static constexpr const char* RpgRoot         = "assets/data/rpg";
    static constexpr const char* Quests          = "assets/data/quests.json";
    static constexpr const char* Shops           = "assets/data/shops.json";
    // ... 等等
};
```

`ContentCatalogLoader` 提供一组 `ensureXxx()` 静态函数，每个负责一类 catalog 的"懒加载 + 校验"。`RpgCatalogLoader` 单独处理 RPG 数据（actors / classes / skills / states / equipment / enemies / troops），因为它分散在 `assets/data/rpg/` 下的多个文件里，需要走 manifest 加载。

**集中 manifest 的两个好处：**

- **改路径不改装配代码。** 新版本想把数据搬到 `assets/data/v2/items.json`？只改一行 manifest 即可。
- **加内容有固定模板。** 新增一类 catalog 的流程是固定的：在 manifest 加一行 → 在 `system_bundle.h` 的 `GameRuntimeServices` 加一个智能指针字段 → 在 `ContentCatalogLoader` 加一个 `ensureXxx()` → 在 `RuntimeServiceFactory::assemble` 调用一次。不会漏，也不需要猜。

### 6. ServiceLookup 与 `registry.ctx()`：场景层"找服务"的统一入口

`GameScene` 持有 `GameRuntimeServices`（所有权）。`SystemFactory` 创建 system 时，硬依赖通过构造函数显式传入——这是主流路径。

但 UI 场景、调试面板或一些跨模块 helper 不适合从 `GameScene` 一路传参。这时候可以用 `entt::registry::ctx()` 找到少量共享服务。

`runtime_service_factory.cpp` 里的典型套路：

```cpp
void injectCatalogPointers(entt::registry& registry, GameRuntimeServices& services) {
    injectRegistryContextPointer(registry, services.rpg_catalog.get());
    injectRegistryContextPointer(registry, services.quest_catalog.get());
    injectRegistryContextPointer(registry, services.shop_catalog.get());
}
```

UI 控件需要本地化服务时，用一个统一的 helper（[`service_lookup.h`](../../src/game/runtime/service_lookup.h)）：

```cpp
inline LocalizationService* findLocalizationService(entt::registry& registry) {
    auto** service = registry.ctx().find<LocalizationService*>();
    return service ? *service : nullptr;
}
```

**为什么用 `registry.ctx()` 而不是全局单例？**

- **生命周期跟 Scene 走。** Scene 退出，ctx 里的指针自然失效，不会出现"场景都销毁了服务指针还悬着"的问题。
- **测试时可替换。** 跑单测时构造一个独立的 registry，注入测试用的 service mock，场景代码完全不变。
- **避免 UI 层一路传指针。** 覆盖式场景和 tab 内容越来越多，如果每个构造函数都追加本地化、catalog、world 等指针，参数列表会失控。`registry.ctx()` 让少量共享服务可以按需查找。

> `registry.ctx()` 里的指针**不表达所有权**，所有权仍在 `GameRuntimeServices`。读代码时把它理解为"这个 Scene 生命周期内可访问的共享服务表"即可。

### 7. Blueprint 与 EntityFactory 在流水线中的位置

上一期 [part-23](../ref/OpenGL与迷你农场/23-蓝图与实体工厂.md) 讲过 Blueprint 与 EntityFactory：把"角色 / 动物 / 作物"的组件组合从 C++ 类型挪到 JSON 描述。这套机制在 TinyFarmRPG 完整保留：

- `BlueprintManager`（`src/game/factory/blueprint_manager.*`）：管理 actor / animal / crop 三类蓝图。
- `EntityFactory`（`src/game/factory/entity_factory.*`）：按蓝图 id 把组件挂到 entity 上。

它们在新项目装配流水线中的位置：

```mermaid
flowchart LR
    A["ContentCatalogLoader<br/>加载 actor / animal / crop 蓝图"] --> B["BlueprintManager"]
    B --> C["EntityFactory<br/>依赖 BlueprintManager + AppearanceCatalog"]
    C --> D["MapManager<br/>切图时调用 factory 实例化对象"]
```

本节课只标记"它们在流水线的哪个位置"。**脚本化 NPC、商人、`scripted_interaction=true` 等 blueprint 字段扩展**会留到 [脚本事件桥与 Tiled 接入](08-脚本事件桥与Tiled接入.md) 详深。

## 小结

这节课的核心就一个词：**委托**。

- TinyFarmRPG 在 `engine / game` 两层之上长出了 `domain`（规则真相）与 `script`（内容编排）两个新角色。
- `GameScene` 不再"手动 new"任何 service 或 system，而是把装配委托给 `GameRuntimeAssembler` → `RuntimeServiceFactory` / `SystemFactory` 的固定流水线。
- 装配顺序由"依赖前置"硬约束：catalog → world → map → save → script。任何一步失败都会中断装配并 `return false`。
- 共享服务通过 `registry.ctx()` 注入，UI 与 system 用 `service_lookup` helper 取出——避免"到处传指针"。

装配解决的是"东西怎么进来"。那"东西怎么写回去"呢？下节课见。
