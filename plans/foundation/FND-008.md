## 已确认约束
- 范围对象：本阶段仅对 `player` 启用分层外观，NPC/动物维持现状。
- 运行时切换：首批仅开放 `hair` 的运行时切换；其他 slot 先保证数据可配置与存档可恢复，不开放交互入口。
- 架构约束：采用“单实体 + 多层运行时数据”，不采用主从子实体拆分。
- 调度约束：本任务不新增 `SchedulerStage::Appearance`，避免引入并行资源竞争复杂度。

## 目标
- 从“单 Sprite 角色”升级到“多层组合角色”，支持 `skin/hair/clothes/eyes/acc/weapon` 的分层渲染。
- 复用现有动画时序，不改动作状态机与碰撞逻辑，保证行为不回退。
- 支持运行时切换至少 1 个部件（首批锁定 `hair`），并能在读档后恢复外观选择。

## 范围
- 新增外观数据模型（slot、variant、layer order）与运行时组件。
- 渲染链路支持“同一实体多层提交”，并与现有 `AnimationComponent` 帧同步。
- 接入素材根目录：`assets/farm-rpg/Character and Portrait/Character/PNG`。
- 接入最小换装入口（debug 面板 + command），仅覆盖玩家实体且首批仅开放 `hair`。
- slot 分期：`skin/eyes/clothes/acc/weapon` 本期先打通“数据配置 + 渲染 + 存档恢复”，不开放交互切换。
- 眼睛层接入性别目录规则（`Eyes/Male` / `Eyes/Female`）。
- 武器层接入动作可见性规则（无武器动作自动隐藏）。
- 外观目录映射统一落在 `appearance_catalog.json`（含 `action_dirs` 与 `slot_dirs`）。
- 接入 `appearance_state` 存档读写。

## 非目标
- 不实现完整“装备系统/属性系统/UI换装界面”。
- 不在本任务中把 NPC/动物改成分层外观（仅玩家链路打通）。
- 不做渲染批处理深度优化（先保证正确性，性能优化放后续任务）。

## 当前基线
- 当前角色渲染链路：`AnimationSystem -> SpriteComponent -> RenderSystem`，每实体仅绘制 1 个 Sprite。
- 玩家动画资源来自 `assets/farm-rpg/Character and Portrait/Character/Pre-made/Alex/*.png`，由 `actor_blueprint.json` 配置驱动。
- `appearance_state` 已在 `schema v3` 预留，但结构仍为空对象。
- `AnimationSystem` 当前只处理同时拥有 `AnimationComponent + SpriteComponent` 的实体，且负责推进帧号与动画事件。
- `MapManager` 现有视觉修正逻辑（如宝箱开盖）直接读取实体 `SpriteComponent`。
- 分层素材真实目录名存在特殊命名约束：
  - `skin -> Skins`
  - `eyes -> Eyes`
  - `hair -> Hair's`（带 `'`）
  - `clothes -> Clothers`（素材原始拼写）
  - `acc -> Acc`
  - `weapon -> Weapons`（仅部分动作目录存在）
- 已确认分层素材目录与动作帧契约：
  - 素材根目录：`assets/farm-rpg/Character and Portrait/Character/PNG`
  - 与当前单图素材“尺寸与帧顺序一致”（可直接复用现有帧索引/方向行规则）
  - 当前玩家动作映射可直接落地：
    - `idle` -> `1. Idle`
    - `walk` -> `2. Walk`
    - `hoe/pickaxe` -> `4. Pickaxe, Hoe and Catching insects`
    - `axe/sickle` -> `5. Axe and Sickle`
    - `watering` -> `7. Watering`
    - `planting` -> `13.4 Carrying - Throwing items`

## 方案比较
1. 子实体方案（每层一个子 entity）
- 优点：少改 RenderSystem。
- 缺点：需要新增主从实体生命周期与同步系统；对现有动画推进与事件链路侵入更大；会显著放大清理、快照与调试成本。

2. 统一实体 + 分层组件方案（推荐）
- 优点：保持“一个角色=一个实体”，不破坏现有 gameplay 查询；直接复用现有动画推进；对存档/地图/调试链路最稳。
- 缺点：需要改 RenderSystem 和外观组装逻辑。

3. 运行时合图（RenderTarget 预合成）
- 优点：draw call 低。
- 缺点：换装频繁时重建纹理成本高，且实现复杂度过高，不符合“先框架”目标。

结论：采用方案 2（统一实体 + 分层组件）。

## 冲突项与取舍（综合 `plans/tmp/FND-008-layered-appearance.md`）
1. 分层承载方式  
选择：`单实体 + LayeredSpriteComponent`。  
理由：若主实体移除 `SpriteComponent`，现有 `AnimationSystem` 将不再推进该实体动画帧与事件；单实体方案可直接复用现有动画主链路。

2. 是否新增 `LayeredAnimationSystem`  
选择：不新增独立动画同步系统，改为：
- `AppearanceSystem` 在 slot 变更时重建“`animation_id -> texture_id` 分层映射缓存”；
- `RenderSystem` 每帧按 `AnimationComponent.current_animation_id_` 查缓存绘制各层。  
理由：动画切换无需重建缓存；避免在 scheduler 增加每帧同步系统与并行资源声明复杂度。

3. 配置落点  
选择：保留单一 `appearance_catalog.json`，吸收 Claude 方案中的 `action_dirs/slot_dirs/gender` 规则。  
理由：减少配置分裂（`catalog + mapping` 双文件）和同步成本。

4. 性别与武器规则  
选择：采纳。  
理由：这是素材结构的真实约束，能明显减少运行时路径拼接歧义与空贴图。

5. 运行时换装范围  
选择：仅 `hair` 暴露调试入口，其余 slot 先做数据与存档通路。  
理由：与你已确认的阶段目标一致，且可把风险控制在最小闭环内。

6. 是否改动 Scheduler  
选择：本任务不改 `system_scheduler`（不新增 `Appearance` stage）。  
理由：当前设计已把“每帧选择动作贴图”的工作放在 RenderSystem 的只读查表路径；`AppearanceSystem` 仅在命令触发时重建缓存，不需要 scheduler 参与。

7. 分层模式下主层是否继续绘制  
选择：分层角色不直接绘制主实体当前 `SpriteComponent` 纹理；由层序中的 `skin` 层作为最底层。  
理由：避免与 Pre-made 合成图重复叠加；同时保留主 `SpriteComponent` 供动画帧推进与兼容现有依赖读取。

## 实现思路（最优方案）
1. 新增外观目录索引与映射规则  
说明：`appearance_catalog` 统一维护 `action_dirs`、`slot_dirs`、默认 profile、可选 variant、gender 规则，并预计算 `action -> available_slots` 矩阵。

2. 新增外观组件并保留主实体 `SpriteComponent`  
说明：主实体继续参与现有动画推进（帧号、事件、翻转）；`AppearanceComponent + LayeredSpriteComponent` 维护按层的 `animation_id -> texture_id` 映射缓存。

3. 扩展 RenderSystem 多层提交  
说明：RenderSystem 对分层角色改为“跳过主纹理、按层绘制”：
- 层顺序固定：`Skins -> Eyes -> Clothers -> Hair's -> Acc -> Weapons`
- 每层按 `current_animation_id` 查 `texture_id`
- 复用主层当前帧的 `src_rect/pivot/flip/size`
- 深度偏移使用 `slot_index * 0.0001f`（不破坏实体间 YSort）

4. 新增 AppearanceSystem（命令驱动）  
说明：处理 `SetAppearanceSlotCommand`（首批仅 `hair`），做 variant 校验、路径解析，并重建 `LayeredSpriteComponent` 的分层贴图缓存。

5. 接入动作可见性规则  
说明：weapon 层根据当前动作映射动态显示/隐藏；无对应武器素材的动作自动跳过该层绘制。

6. 接入装配与资源注册  
说明：runtime 启动时加载 `appearance_catalog`；玩家创建时挂载默认 profile；资源预注册采用“默认 + hair 可切换白名单”策略。

7. 接入存档 `appearance_state`  
说明：`SaveService::capture/apply` 读写玩家 slot 选择（至少 `hair`），读档后触发一次外观重建。

8. 先保障正确性，再做性能观察  
说明：首版优先“正确性 + 稳定性”，draw call 变化先通过 debug 面板与回归测试跟踪。

## 验收标准（DoD）
- 玩家实体渲染可同时提交多个外观层，且与当前动作帧严格同步。
- 动画状态切换（如 `idle -> walk -> hoe`）时，各层贴图可基于 `current_animation_id` 自动切换，无需再次发送换装命令。
- 运行时可切换至少 1 个部件（`hair`）并立即生效。
- 现有动作链路不回退：移动、工具动作、碰撞、交互行为保持正确。
- 读档后可恢复玩家外观选择（`appearance_state` 生效）。
- 新增/更新测试通过，`build/debug` 全量回归通过。

## 风险与缓解
- 风险：分层资源数量大，可能造成内存与加载时间上升。  
缓解：首批仅注册默认+调试可选的白名单 variant，后续再增量扩展。

- 风险：素材命名不一致（大小写/空格/拼写）导致路径匹配失败。  
缓解：catalog 显式列出可用 variant；加载阶段输出缺失清单并回退默认层。

- 风险：动作目录映射缺项导致某些动作层丢失（尤其 weapon）。  
缓解：`action_dirs` 在启动时做完整性校验，缺项直接回退主层并输出告警。

- 风险：多层叠加导致 draw call 增长。  
缓解：先保证功能正确，记录渲染统计；后续在独立任务做批处理优化。

- 风险：存档恢复外观后若未触发重建，显示与数据不一致。  
缓解：`SaveService::apply` 后显式触发外观重建路径（或统一走 command）。
